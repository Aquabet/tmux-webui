# 项目现状与路线图

[English](project-roadmap.md)

本文记录截至 **2026-08-08** 的工程状态、产品定位与建议执行顺序，供维护者规划
后续工作。它不是承诺所有条目都会上线。开始新阶段前，应重新检查依赖漏洞、同类
产品等具有时效性的信息。

## 执行摘要

tmux-webui 已经是可用的首个正式版本，不是原型。它具备安全意识明确的本地部署
模型、经过测试的 tmux 视图生命周期、手机终端体验、持久登录会话、agent 状态
标记，以及可恢复的一键更新流程。

下一步不应追求通用终端功能对齐。成熟工具已经覆盖这个方向，而 agent 产品也在
快速加入 worktree 管理、diff 审查、沙箱和结构化 agent 接口。tmux-webui 应保持
更窄的定位：

> 不迁移现有工作流，直接连接已有 tmux session 的私有手机伴侣，并提供一个可选的
> coding agent 待处理收件箱。

这个定位保留了项目最强的特性：使用用户自己已有的 session，不替代 tmux，不读取
agent transcript，并继续把远程访问交给用户已有的私有网络或 TLS 反代。

## 应保持稳定的架构

```text
浏览器
  |-- 已认证 HTTP --> Express API --> tmux 命令 / 主机资源
  `-- 已认证 WS ----> node-pty ----> tmux 分组视图
                                      `----> 用户现有 session

Agent lifecycle hooks/plugins
  `-- 少量 tmux pane options --> session 列表 --> 侧栏 badge
```

当前架构做出了几项合理取舍：

- 浏览器连接会创建临时 tmux 分组 session，可以独立切换 window 和调整尺寸，不干扰
  本地已连接的 tmux client。
- 终端字节只穿过 WebSocket 与 PTY 层，服务端不解释 shell 命令或 agent 对话。
- Agent 集成通过 tmux option 上报少量生命周期状态，不读取 prompt、终端输出、
  transcript 或凭据。
- 配置只在一处读取，外部值统一验证。
- 自更新 HTTP 请求不接受分支、ref、路径或命令；固定更新器会先确认 systemd 指向
  当前 checkout，再进行修改。

这些约束是产品的一部分，不是偶然的实现细节。除非单独完成设计和安全评审，新功能
都应保留这些约束。

## 值得继续利用的优势

### 现有 tmux session 是唯一事实来源

用户不需要把 session 迁移到项目自带的编排器。本地 tmux client 与浏览器视图可以
并存，关闭浏览器也不会终止后台工作。

### 手机交互解决了真实终端问题

原生输入条支持系统输入法、语音输入、滑行输入、终端控制键、长按退格和图片路径
插入。触摸滚动同时覆盖普通 scrollback 和开启 mouse tracking 的 TUI。

### 早期项目里少见的失败处理

前端使用有上限的指数退避重连 WebSocket。安装脚本会先检查前置依赖。更新器能区分
构建、service 和重启失败，且只有重启后的服务持续存活才会报告成功。

### 安全默认值符合产品后果

默认只监听 `127.0.0.1`。登录使用 bcrypt、限速、随机 session token，以及
HttpOnly `SameSite=Strict` Cookie。WebSocket 连接必须携带有效 session，并拒绝
Origin 不匹配的浏览器请求。

## 扩大使用前仍需补齐的缺口

版本 `3.1.8` 已清除已知依赖漏洞，把浏览器测试和静态质量检查纳入 CI，限制
WebSocket 缓冲，加固上传存储，并增加明确的 HTTP 安全响应头。Dependabot 现在会
持续检查两个 npm workspace。

### 文档与界面语言不一致

项目同时维护中英文 README，但大多数可见 UI 文案是中文。如果产品坚持中文优先，
这没有问题；如果英文 README 仍是受支持入口，它就会成为使用门槛。

## 产品定位

[ttyd](https://github.com/tsl0922/ttyd) 等通用网页终端已经提供广泛平台支持、
打包安装、TLS 选项、文件传输与终端渲染能力。[Agent of Empires](https://github.com/agent-of-empires/agent-of-empires)、
[Agentboard](https://github.com/gbasin/agentboard) 和
[Coder Mux](https://github.com/coder/mux) 等 agent 产品也已经覆盖 worktree 管理、
diff 审查、agent 编排、远程主机与结构化 agent 视图。

逐项复制这些产品会扩大安全边界，也会抹掉 tmux-webui 的简单性。建议聚焦：

- **现有 session 优先。** 连接用户已经在运行的内容。
- **默认私有。** 坚持回环监听，并把外部 TLS/私有网络作为硬要求。
- **不读取内容的状态。** 优先 lifecycle hook 和进程身份，不解析 transcript。
- **手机注意力闭环。** 快速发现哪个 session 需要人、进入处理，然后离开。
- **小型运维边界。** 在真实使用证明更大模型值得之前，保持单用户、单主机。

## 路线图

### 阶段 0：`3.1.8` 安全与质量基线

**状态：已于 2026-08-08 完成。** 这是维护版本，不增加新产品表面。

#### P0.1 更新依赖

范围：

- 升级 Express/body-parser，得到没有已知漏洞的生产依赖图。
- 联动升级 Vite、Vitest、PostCSS、nanoid 和相关插件。
- 加入自动依赖更新，并把前端工具链合并更新，避免大量单包 PR。

验收条件：

- `npm audit --omit=dev` 不报告已知生产漏洞。
- 完整审计没有 high 或 critical 项。
- 类型检查、构建、308 个单元/集成测试和 6 个浏览器测试通过。

#### P0.2 在 CI 运行浏览器测试

范围：

- 在一个受支持 Node 版本上增加 Chromium Playwright job。
- 在该 job 中安装 tmux 和 Playwright 浏览器。
- 继续使用隔离的 `webui-e2e` tmux socket 与专用端口。

验收条件：

- 登录到终端的路径失败时，PR 无法合并。
- Job 每次都清理 tmux server，不依赖上一次构建产物。

#### P0.3 限制 WebSocket 资源占用

范围：

- 定义并测试明确的 WebSocket 最大消息尺寸。
- 限制 PTY 初始化前的排队帧数量与总字节数。
- 用稳定 close code 关闭滥用连接并释放对应视图。
- 为慢客户端增加输出背压，或定义清楚且有界的处理策略。

验收条件：

- 超大输入无法无限增加服务内存。
- 普通终端粘贴、resize、window 切换与重连仍通过单元和浏览器测试。

#### P0.4 加固图片存储

范围：

- 以仅属主权限创建上传目录。
- 以仅属主权限写入文件。
- 增加可配置的保留时间和总存储配额。
- 清理过期文件时不跟随符号链接，也不删除配置目录以外的内容。

验收条件：

- 测试覆盖权限、配额拒绝、过期清理和路径边界。
- 现有 PNG、JPEG、WebP、GIF 上传保持可用。

#### P0.5 增加 HTTP 安全响应头

范围：

- 设置与 xterm 和构建产物兼容的 Content Security Policy。
- 禁止页面被嵌入、关闭 MIME 嗅探，并设置保守的 referrer policy。
- 说明哪些 TLS 与 HSTS 责任仍属于反向代理。

验收条件：

- 服务端测试断言所有响应头。
- 生产终端渲染、WebSocket 连接和内联 SVG 图标保持正常。

#### P0.6 补齐质量门禁

范围：

- 配置支持 TypeScript 的 lint 和 formatter。
- 对仓库 shell 脚本运行 ShellCheck。
- 增加死代码检测和实际覆盖率测量。
- 从当前基线设定门槛，此后阻止回退。

验收条件：

- 所有检查都有文档化的本地命令，并进入 CI。
- 对生成物和平台相关脚本只做窄范围、有理由的排除，不使用全局关闭。

### 阶段 1：`3.14.0` agent 待处理收件箱

这个阶段把已有状态 badge 变成完整工作流，但不把 tmux-webui 变成 agent 编排器。

#### P1.1 增加待处理视图

- 按 `waiting`、`running`、无上报状态排序或过滤 session。
- 明确等待用户回应的 session 置顶。
- 显示最近一次状态变化时间，不显示终端或 prompt 内容。
- 普通 tmux session/window 导航仍是默认视图。

#### P1.2 增加自愿开启的浏览器通知

- 只在有意义地进入 `waiting` 时通知。
- 对重复 hook 上报去重。
- 通知保持不读取内容：只包含 agent、session 名和状态。
- 第一版只覆盖页面打开或位于后台时的通知。关闭页面后的 Web Push 需要单独的
  安全与密钥管理设计。

#### P1.3 诊断 agent 集成

- 显示每个 provider 最近是否上报过 lifecycle event。
- 区分未安装集成、状态过期和 agent 空闲。
- 直接链接到 agent 状态文档中的对应安装章节。

#### P1.4 增加 session 搜索和键盘导航

- 不修改 tmux 名称即可过滤 session 和 window。
- 提供可预测的上一个/下一个待处理快捷键。
- 所有动作同时支持触摸与纯键盘操作。

#### P1.5 界面国际化

- 把可见文案和无障碍标签移入小型、带类型的 message catalog。
- 提供英文和简体中文，支持浏览器语言检测和显式覆盖。
- 让服务端错误码足够稳定，使客户端可以翻译已知错误，同时保留未知诊断信息。

阶段验收条件：

- 用户在手机上最多三次操作即可发现等待中的 agent、进入正确 session、回应并返回
  session 列表。
- 不读取或存储终端历史、prompt 或 agent transcript。
- 只有用户主动操作后才请求通知权限。
- 所有新行为都有前端测试，并至少有一条浏览器级流程。

### 阶段 2：分发与验证

这部分应与阶段 1 并行，不必等大功能版本完成。

#### P2.1 让用户安装前就看懂产品

- 在 README 增加最新桌面与手机截图。
- 录制短演示，覆盖登录、切 session、手机输入与 agent 等待交接。
- 在顶部明确单主机、单用户、私有网络定位。

#### P2.2 只选择一条受支持的打包路径

当前 Git checkout 和 systemd 安装器可靠，但步骤比同类工具多。先评估一个主要渠道：

- 可以安装和管理 user service 的 npm 全局包；或
- 带校验和的小型安装器与 release archive。

不要同时增加多条维护不完整的渠道。所选方案必须保留前置检查、password-stdin、
安全 service 归属和可验证更新。

#### P2.3 招募外部用户

先找 5 到 10 位已经使用 tmux 且至少运行一个受支持 coding agent 的用户。测量：

- 安装完成率和首次看到终端所需时间；
- Node、node-pty 编译、tmux、systemd 或网络导致的失败；
- 手机重连和输入失败；
- 等待状态有多少次带来了有效回应；
- 哪个缺失能力阻止用户继续使用。

对于一个提供 shell 权限的工具，加入产品遥测前应优先采用直接访谈和 issue 反馈。

## 明确不做

除非用户证据改变定位，以下内容不在建议路线图中：

- 直接暴露到公网。
- 多用户账号、角色权限或共享终端。
- 远程 SSH 主机清单与凭据管理。
- Git worktree 编排、内置 agent loop 或 Docker 沙箱控制。
- Transcript 解析、prompt 历史或终端内容索引。
- 完整 IDE、编辑器或 diff 审查系统。
- 取代 tmux 管理 session、window、pane 或持久化。

每一项都会明显扩大信任边界，需要单独的产品和安全评审，而不只是多加一个 endpoint。

## 建议执行顺序

| 顺序 | 交付物 | 为什么现在做 |
|---|---|---|
| 1 | 依赖升级和自动更新 | 消除已知风险与后续维护漂移 |
| 2 | 浏览器 E2E 进入 CI | 保护真实的登录到终端路径 |
| 3 | WebSocket、上传和 HTTP 加固 | 限制已认证滥用与本机数据泄露 |
| 4 | 质量门禁 | 让当前干净基线可以持续 |
| 5 | 待处理收件箱和通知 | 扩展项目最强的差异点 |
| 6 | UI 国际化和搜索 | 提高覆盖范围和日常导航效率 |
| 7 | 打包与外部验证 | 判断产品是否值得继续扩大投入 |

## 新想法的判断规则

在加入新路线图条目前，先问：

1. 它是否让已有 tmux session 更容易远程使用？
2. 它是否缩短了手机上从“agent 需要我”到“我已经回应”的路径？
3. 它能否在不读取终端内容、不接管开发工作流的情况下实现？
4. 它是否保留默认回环监听？
5. 它的失败路径能否在不影响用户真实 tmux session 的前提下测试？

同时不满足多项条件的想法仍可能有价值，但更可能属于另一个产品，或需要明确改变
当前战略。
